## Original findings — both now fixed

### F1 — P2, FIX VERIFIED: a released family drop target retains itself and its owners

**Location:** `Attic/Views/Panel/SubtaskPanelContent.swift:290–293`, `configureFileDrop`; stored callback in `Attic/Views/Panel/TaskAttachmentDrop.swift`, `TaskFileDropTarget.perform`.

**Trigger:** present a family surface, then close/recreate pinned surfaces (or otherwise dispose of their SwiftUI state). Every configured target owns `perform`, and `perform` strongly captures the same `fileDrop` in `fileDrop.end()`. Reconfiguration replaces one self-capturing closure with another. There is no callback teardown when the view disappears. `closePinned` removes the window from the controller, but cannot break this ARC cycle.

**Cause and impact:** `TaskFileDropTarget → perform closure → TaskFileDropTarget` remains alive after all external target ownership ends. The closure also retains the store and controller. Repeated panel creation/disposal accumulates orphan targets/closures; retained owners cannot be released through this path. This is new V2 code, contrary to the requested efficient resource lifecycle. The exact size of a leaked live UI graph was not measured, so this is not a claim that every closed window is retained.

**Executed evidence:** a standalone Swift probe compiled the actual extracted `TaskFileDropTarget` type and assigned the exact self-capture pattern. After its external strong variable left scope, a weak reference remained non-nil. Clearing `perform` made that weak reference nil:

```
Released drop target remains alive: true
Clearing callback releases target: true
```

This proves the ARC cause without depending on a UI-memory interpretation; it does not replace an installed-window teardown test.

**Small fix:** weakly capture the drop target in its stored callback, while preserving `end()` and parent/mode routing; use a narrow configuration seam if needed so a regression test exercises the production callback setup. If adding explicit teardown, ensure appear/family/mode reconfiguration restores both callbacks and does not disable a promoted/reused surface. A weak capture is sufficient to break this particular cycle.

**Focused verification:** configure/reconfigure a target through the production setup, release its external owner, assert a weak target deallocates; retain the existing routing and whole-panel highlight-clearing tests. Then open/pin/close/reopen once in the preview to ensure the destination still accepts drops.

### F2 — P2, FIX VERIFIED: a busy hover-close retries at an already-expired deadline

**Location:** `Attic/Window/SubtaskPanelController.swift:381–383`; downstream zero-delay scheduling at `:276–283`; idempotent close deadline at `Attic/Services/SubtaskPanelLayout.swift:550–555`.

**Trigger:** hover-open a family, activate/type into its Add subtask entry or begin editing a child, then move the pointer clearly outside the panel/corridor while that interaction remains protected. The panel is still hover-origin: `addAffordance` activates the entry without latching the surface. Its focus/draft or family edit makes `shouldDeferPointerClose` true.

**Cause and impact:** when the close deadline matures, the busy branch calls `noteRowHover(false)` and reschedules. `scheduleClose` deliberately preserves an existing close for that family, so its old, expired deadline remains. `max(0, pending.deadline - now)` therefore becomes zero. The next main-queue callback takes the same branch and schedules immediately again. This can repeatedly allocate/cancel dispatch work and sample the pointer on the main thread for the duration of a normal edit/draft lock. It wastes CPU and can degrade responsiveness. It is an asynchronous busy loop, not synchronous recursion.

**Baseline attribution:** confirmed in the approved baseline tree: the same busy branch, idempotent `scheduleClose`, and zero-delay scheduler already existed. It is not caused by the new travel algorithm. It is still an actionable blocker for this requested overall resource audit, rather than a request to revisit an accepted visual preference.

**Executed evidence:** a standalone Swift probe used the actual extracted `SubtaskPanelLifecycle` with the production timing constants. It opened a hover family, scheduled leave at t=1, and invoked the busy branch's repeated leave at t=2. Output:

```
Busy close retry original deadline=1.1400000000000001
retained deadline=1.1400000000000001, dispatch delay at t=2: 0.0
```

The controller source supplies the immediate rescheduling edge. No live app was deliberately put into this CPU-heavy state, and no measured CPU percentage is claimed.

**Small fix:** stop dispatching an expired close while an interaction lock is active and resume/re-evaluate that pending decision on the relevant lock change. Preserve family identity, current pointer/corridor classification, entry/draft protection, and the ability to close once protection ends without needing a new hover event. Explicitly moving the deadline forward would remove the zero-delay spin, but an indefinite timer that polls the lock is weaker than the user's no-poller requirement; prefer an event-driven wakeup from the already-observed UI state. Do not alter ordinary repeated-leave idempotence to fix this, since it protects against perpetually postponed closes.

**Focused verification:** a controller test should hold an outside-pointer close behind an active draft/edit lock across multiple would-be deadlines and prove no immediate callback churn; clearing the lock must produce one appropriate close/re-evaluation without another hover callback. Cover arrival, family replacement and teardown while suspended, plus the existing corridor/latched/dragged tests.

## Resource and regression audit

- **File cost:** regular imports stream 1 MiB chunks, with 15 MiB/item, 20 items and 100 MiB/task limits; task imports request no in-memory payload. Image validation uses a file URL with caching disabled. File-provider staging may temporarily accumulate up to 20 × 15 MiB before the final task-total check, but is bounded and is removed by the staging owner's success/failure cleanup. No image copy occurs during card layout, window move or resize.
- **Display cost:** thumbnails are generated on demand through the file actor, capped at 512 pixels and a 64-entry encoded cache. Row requests are 96 pixels and gallery requests 256 pixels. Hash verification reads the bounded file on preview/open/drag or an uncached thumbnail request; cross-owner copy legitimately performs additional verification/copy I/O. Cache bounds are entry-count bounds, not measured RSS/energy figures.
- **Observation/layout:** focused title disclosure installs observers only while presented; teardown removes them. Gallery uses a lazy grid; row metadata still decodes small reference arrays and scans the current store in computed properties. Measured heights ignore subpixel changes, surface animation targets deduplicate repeated fits and weakly identify windows. The general control policy intentionally affects Notes/Canvas controls too. F1 is the outstanding new callback-lifetime leak; F2 is the outstanding callback scheduling defect.
- **Cleanup:** private abandoned task copies are swept once at interactive persistent-store startup, protecting every physical replica, recently created/modified copies and unknown/symlink entries. The 500 limit bounds materialization removals, not total directory enumeration or staging cleanup work. Temporary exports age out when another export is made. This is source-level bounded-work assessment, not a large-library benchmark.
- **Retained application behavior:** baseline-tree byte comparisons showed all 19 `Attic/Canvas` files, `AtticPanel.swift`, `AtticPanelController.swift`, `NoteStore.swift`, `NotesPanelContent.swift` and `CanvasPanelContent.swift` unchanged from the approved dirty baseline. Main motion and Canvas/Notes implementation were not replaced. Shared changes were inspected: optional ImportedAttachment payload keeps Notes' original default, Note Open policy refactor is equivalent, and `NoteInlineCardsLayout.dragType` only becomes nonisolated. No new CloudKit/APNs activation or legacy-store migration introduced.
- **Measurement limits:** the earlier UX idle sample is historical baseline evidence only. No fresh V2 idle/large-attachment/energy measurement was taken by this reviewer. In particular, the inherited unlocated QoS warning is not attributed to F2 without a stack/sample connecting them.
