## O-1: resize — initial checkpoint

### DP-1 (P1, suspect): Every changed size publishes through the shell as well as AppKit layout
- Chain: `Attic/Window/AtticPanel.swift:2287–2302, 2333–2358, 2441–2445` → `Attic/Window/AtticPanelController.swift:1029–1036, 1230–1234` → `Attic/Window/PanelUIState.swift:200, 352–359` → `Attic/Views/Panel/AtticPanelView.swift:52–71, 145–149, 186–217`.
- Trigger: custom grip drag. Every delivered drag computes a frame, synchronously calls `setVisibleContentFrame(..., display: true)`, and calls `updatePanelSize`; `windowDidResize` also calls it. The 0.25-point equality guard prevents a second publication for an identical size; do not assume two actual publications per event. Each changed publication feeds `PanelRelevantUIStateObserver.objectWillChange` for the root shell, whose `panelSize` drives `PanelPageLayout`, page transitions and kept page positions. This is additional SwiftUI state propagation on top of the already assigned single-host hidden-page layout issue, not a claim that the existing hosting-layout fix solves resize.
- Scaling: approximately one root publication per distinct size (not necessarily per input event after the guard), plus work in size-dependent descendants; cost can grow with mounted pages and their current content. The exact number of body evaluations and AX updates is not established by static code. `settings.persistPanelSize` occurs at `endLiveResize` (controller 1265–1277), not on each drag, so per-frame preference writes are not supported by this path.
- Smallest cause-level direction: coalesce size publication to the latest size per display frame and isolate size-dependent shell/layout inputs from unrelated state, while AppKit remains authoritative and the actual visible geometry, hit regions and resize interaction stay live. Test whether eliminating the duplicate path is sufficient before changing architecture.
- Confidence: high for call chain, medium for contribution to visible jank. No independent attribution in milliseconds.
- Mac measurement: add signposts around `mouseDragged`, `setContentFrame`, `updatePanelSize` changes, root body and `panel_host_layout`; correlate event IDs and count per display frame, AX on/off, with 1 vs 5 previously built pages and 10/1,000 tasks. Count emitted panel sizes and root evaluations; ensure visual resize follows each presented frame. Guard test: feed a burst of size inputs to a controlled frame scheduler and assert at most one publication per frame, latest size delivered, and exact final size on release. Do not assert wall-clock timing.

### DP-2 (P1, suspect): Island follows resize through separate native windows and a size-dependent glass tree
- Chain: `AtticPanelController.windowDidResize` (1230–1235) → `layoutIsland` (1910–1917) → `PanelIslandWindows.layout` (`Attic/Window/PanelIsland.swift:1393–1404`). It calculates frames and, when changed, calls `setFrame(..., display: island.isVisible)` on the island and label windows; the stand-in is placed as well. Independently the changed `$panelSize` reaches `PanelIslandKeyed` (1095–1107), which updates its environment and `PanelIslandSurface` (944–975), including native glass sizing, multiple shadow layers and an offscreen destination-out mask.
- Scaling: up to two changed native child-window frame commands and one island size-state change per distinct resize step; visual material/mask work is fixed per island rather than per task. Window geometry may differ only on some resize edges and the equality checks avoid redundant `setFrame`s. Whether SwiftUI/AppKit recomputes or composites those layers on each change must be measured; do not assert GPU cost as measured fact.
- Smallest fix: coalesce frame positioning and island environment updates to one latest-frame transaction per display refresh; skip the label frame command when the computed frame is unchanged. Preserve the exact glass, shadows, alignment and accessibility. Do not replace or flatten the accepted look without visual equivalence.
- Confidence: high for call chain and per-change work, medium for contribution; likely smaller than large hidden-page layout until profiled.
- Mac measurement: signpost `windowDidResize`, island layout, each window `setFrame`, stand-in placement, island root/body, Core Animation commits and GPU offscreen passes. Compare with instrumented island updates suppressed in a disposable diagnostic build, not a product recommendation. Guard test: 100 synthetic resize callbacks in one frame produce at most one final island/label placement, no frame drift, and correct final geometry for all corners/spots.

### DP-3 (P1, suspect): Notes table remeasures every cell as width changes
- `Attic/Notes/Engine/NoteTableView.swift:184–199, 328–342` → `Attic/Notes/Engine/NoteTableAttachment.swift:58–87` → `Attic/Notes/Engine/NoteTableLayout.swift:121–135`.
- Trigger: resizing a panel that has a mounted Notes editor containing a table. A table view width change over 0.25 pt invalidates the attachment layout, then `refreshLayout()` requests the new width. A cache miss creates per-cell arrays and `make` visits natural width, minimum width and wrapped height for cells. Text caches can reduce actual text measurement, but new widths can miss height entries. This is a resize-specific path, distinct from PF-11's cell-edit cost. Whether a hidden editor is laid out under the already-known host behavior must be measured.
- Scaling: O(rows × columns) visits and array slots per invalidated table width, plus text measurement for cache misses; multiplied by mounted table attachments and distinct widths. Not all visits necessarily invoke expensive text measurement.
- Smallest fix: preserve natural/minimum per-cell metrics across width-only changes, compute only width-dependent height where its effective column width changed, and coalesce width updates per display frame. Preserve exact wrapping, geometry, selection and accessibility; do not defer visible geometry past its presented frame.
- Confidence: high for explicit loops and cache invalidation, medium for frequency and perceptible cost under AppKit.
- Mac measurement: signpost `setFrameSize`, attachment `layout(width:)`, `NoteTableLayout.make`, and text-cache hit/miss/height measurements; count cell visits per resize frame for 10×5, 100×20 and multiple tables, with Notes visible versus retained hidden and AX on/off. Guard test: unchanged widths perform no full grid recompute; changed widths recompute only affected columns' height metrics and preserve exact row heights and hit geometry.

### DP-4 (P2, stress-scale suspect): Draw recalculates full-scene coverage on every board frame-size call
- `Attic/Draw/Engine/DrawBoardView.swift:161–167, 191–210, 227–257, 262–274`.
- Trigger: resize while Draw's board view receives `setFrameSize`. It invalidates detail, repositions layers and calls `requestRaster`; before comparing `requestedKey`, `currentKey()` calls `rasterCoverage()`, which unions `model.objects` and may also scan moved/replaced objects. A matching key prevents a new world raster, so it would be incorrect to claim every size step rerenders the whole scene. Detail cancellation/rescheduling may still occur on this path when higher-density detail is needed (285–304).
- Scaling: O(number of scene objects) main-thread bounds work per size callback, plus selection/layer geometry; a detail request may be restarted after a 35 ms settling delay. Bitmap work depends on key changes and renderer cancellation, not proven per step.
- Smallest fix: cache scene coverage by content revision and movement/replacement identity; reuse on a viewport-size-only change. Coalesce detail settling without changing displayed content or input mapping. Preserve full-scene coverage and cancellation safety.
- Confidence: high for repeated `currentKey` traversal, medium for its frequency and effect; hidden board behavior and `model.isShown` guard matter.
- Mac measurement: signpost frame-size, coverage computation, object visits, world/detail raster requested/completed/cancelled and frame time; resize a board with 10, 1,000 and 10,000 objects, visible and retained hidden. Guard test: repeated frame sizes with unchanged content visit no scene objects after first cached coverage, and mutation/move invalidates it correctly.

**Floating-panel boundary:** The docked `windowDidResize` path (`AtticPanelController.swift:1230–1235`) updates panel size and island layout; it does not call `PanelPullOutController.place` or move all floating panels. Floating panels are separate windows with their own hosts (`PanelFloatingPanels.swift:24–71`), and their positioning is driven by their own drag/restore paths (`:456–468, 684–695`). Do not count one floating-window frame update per docked resize without a trace. Visible floating windows may still independently respond to shared model changes or window-server composition; measure that separately.

### DP-5 (P1, suspect): Every realized row reports its moving frame while scrolling
- `Attic/Tasks/TasksPage.swift:147–152, 1687–1693, 4548–4557, 4871–4877`; coordinate space established in `Attic/Tasks/TasksPager.swift:665–675`.
- Every realized `TasksReorderCell` uses `onGeometryChange` to observe its frame in the fixed pager-slot coordinate space. As the scroll content moves relative to that slot, frame changes update `reports.frame`, `TasksPointer.localFrames` and `frameOwners`. Headers and Completed Today separately report frames (`TasksPage.swift:1713–1717, 1763–1766`). The dictionaries are deliberately outside observed view state, so do not claim each write triggers a SwiftUI redraw. Scroll-position preference writes are PF-7 and are not re-filed here.
- Scaling: O(realized moving rows + visible/retained headers) geometry comparisons and potential dictionary writes per scroll layout update, not necessarily O(total database rows). The actual callback count and whether LazyVStack retains offscreen cells are framework-dependent.
- Smallest fix: keep row frames in scroll-content coordinates and combine with a single current clip offset when queried, updating row geometry only when actual content layout changes. Preserve hit testing, drag/drop, reveal and simultaneous/retained-page identity; batch only if coordinate correctness is retained.
- Confidence: high for registered observers and writes, medium that every scroll tick changes each reported frame and is a felt bottleneck.
- Mac measurement: count row/header geometry actions and dictionary writes per clip-bounds change and per frame, realized cells, allocations and frame hitches for 100/1,000/10,000 tasks; compare the same scroll trace with a diagnostic content-coordinate implementation. Test: synthetic clip offsets alone must not rewrite every registered row; pointer lookup, context menu, drag/drop and reveal still resolve the right visible row at arbitrary offsets.

### DP-6 (P1, suspect): Context-menu infrastructure mounts native anchors in each realized row

The date/tag `atticDropdown` anchors are conditional on presentation (`AtticDropdown.swift:2444–2455`), so they are not extra native views at rest. H-01 is the separate known focus-responder issue.

Per newly visible row it creates or attaches these objects; it does not necessarily recreate them on every scroll event. Right/Control-click also searches registered context anchors (see DP-7 under O-3 below, if validated).
- Smallest fix: share a page-level context-menu router using the existing row geometry and a single accessibility menu anchor, keeping per-row VoiceOver Show Menu actions routed to the same item. Preserve nested tag menus and keyboard focus. Prove that realization counts fall before adopting the change.
- Confidence: high for two unconditional representable backgrounds per rendered row; medium for measured effect under AX and actual reuse.
- Mac measurement: instrument `makeNSView`, `viewDidMoveToWindow`, `dismantle`, active anchor count, Focus/AX registration and row-body evaluations; use Instruments' SwiftUI and Time Profiler while scrolling 100/1,000/10,000 rows with AX active. Guard test: an ordinary page with N realized rows has O(1) shared anchor views after the change, context/AX actions target the correct row and nested tag menu remains reachable. No wall-clock thresholds.

### DP-7 (P1, context-click suspect): The context-menu router scans registered anchors and their view ancestry

- Smallest fix: narrow candidate anchors by window and spatial region, or route directly from the existing page hit/row geometry while preserving innermost-menu precedence, shields, editable text and VoiceOver Show Menu. Avoid per-click whole-table enumeration.
- Confidence: high for scan/hit-test path, medium for latency contribution; no timing measured.

### DP-8 (P1, first-touch suspect): Approach warmup can run synchronous layout/display/flush immediately ahead of input
- `Attic/Window/AtticPanelController.swift:183–203, 2192–2229, 2233–2250`; `Attic/Services/CornerHoverMonitor.swift:414`.
- A corner or island approach schedules a main-queue block; if still inside, `warmFirstTouchPresentation` can prepare a page, call `layoutSubtreeIfNeeded` on the content and host, display their layers and `CATransaction.flush` before returning. It guards active motion and an already-pressing panel, but a click arriving just after this work starts cannot preempt it. The cost depends on cold/built pages, active accessibility, view count and any previous backlog. A separate delayed kept-page warmer checks recent key/scroll input (`2295–2335`); do not conflate the two.
- Smallest fix: instrument first, then make warming cancellable/cooperatively staged between bounded main-run-loop slices and abandon remaining work when input is queued; use previously prepared layers without forcing extra synchronous display/flush on the critical input path. Preserve first-click correctness, page readiness and visible transitions; never change the accepted appearance.
- Confidence: high for synchronous operations on the queued approach path; medium for how often they overlap the owner's first click or explain any measured latency. Existing warmup may improve other cases, so removing it blindly could regress cold clicks.
- Mac measurement: correlate `warmup_begin`, `warmup_model`, `warmup_layout`, `warmup_layers`, `warmup_end`, physical event timestamps, `panel_host_layout`, AX focus work, CA transaction/commit and WindowServer presentation; A/B cold/warm and AX on/off. Guard test: queue approach then simulated input before the first staged slice and assert it cancels/deprioritizes remaining warmup; first click still reaches its target and page state remains correct.

## Whole-app review — Notes and MCP checkpoint

### DP-9 (P2, long-note suspect): Folded headings make viewport layout scan the full outline for each visible heading
- `Attic/Notes/Engine/NoteEditorTextView.swift:962–975` → `Attic/Notes/Engine/NoteBlockLayout.swift:1049–1094, 1097–1114, 1258–1302`.
- On text-view layout, `updateHeadingControls` obtains visible headings via a binary-searched cached outline. If any heading is folded, each visible heading tests `headingSections.contains` to find a folded enclosing section. That scans the full cached outline until a match; it also sets each visible button's label, frame and `needsDisplay` on the pass. With no folded headings the guard short-circuits, and the outline itself is cached, so this is not an unconditional full document rebuild. It is distinct from the listed PF-10/11 table work and PF-16 Find.
- Scaling: worst-case O(V × H), V visible headings and H total headings, per qualifying layout, plus O(V) native control updates. The exact number of layouts during scroll/resize and whether a heading's position makes the scan end early must be measured.
- Smallest fix: cache or index folded section intervals and query the enclosing interval by position, invalidating on outline/fold changes; avoid reassigning unchanged button geometry/AX labels. Preserve nested-fold semantics, glyph positioning and VoiceOver labels.
- Confidence: high for conditional nested scan, medium for user-visible cost.
- Mac measurement: add counts for `updateHeadingControls`, visible headings, candidate sections examined, changed/unchanged button properties and layout duration. Scroll and resize a 10/1,000/10,000-heading note with one fold near the end and with none; AX active. Guard test: visible-heading queries should scale near O(V log H) with nested folds and exactly match current visibility/labels; do not use timing thresholds.

### DP-10 (P2, bounded background-work suspect): Awaiting MCP approvals wakes every 100 ms
- `Attic/Services/AgentServer/MCPRequestHandler.swift:23–35, 151–156` → `Attic/Agent/Actions/AgentActions+MCP.swift:174–191`.
- An initial tool call waiting on owner approval loops on the main actor, checking state and sleeping 100 ms until resolution or the default 20-second deadline. One unattended request can resume approximately 200 times; concurrent waiting calls multiply wakeups. The loop sleeps rather than busy-spins, is bounded, and this is not PF-34's separate lack of MCP admission bound or PF-40's retained registry growth.
- Smallest fix: suspend on a one-shot continuation or async notification resolved by approval, refusal, cancellation, run end or one deadline task; retain status-poll and socket-deadline semantics and avoid lost wakeups/double resumes.
- Confidence: high for the wakeup pattern, low/medium for real battery or perceptible impact absent measurement.
- Mac measurement: count approval wait resumptions, simultaneous waits, main-actor time and energy/wakeups over a full 20-second unanswered prompt and during active UI work; compare event-driven version. Guard test: zero periodic polls while pending, one completion on each outcome, prompt retry/idempotence preserved, cancellation and timeout tested with a controllable clock.

### DP-11 (P2, large streamed tool-input suspect): Claude JSON fragments are accumulated through copied value state on the main actor
- `Attic/Agent/Run/AgentRunEngine.swift:273–274, 578–592` → `Attic/Agent/Run/AgentCLIStreamDecoder.swift:23–32, 112–135`.
- Every helper line extracts a value copy of the decoder, mutates it and stores it back. For Claude `input_json_delta`, it also extracts a tuple from `claudeInputs`, appends the fragment to its growing `String`, then assigns the tuple back. At block end it converts the whole accumulated string to UTF-8 and parses JSON. The old dictionary/decoder value remains referenced during these operations, so Swift copy-on-write may copy dictionary storage and the accumulated string repeatedly. This is streamed **tool argument** JSON, distinct from PF-30's repeated parsing of the assistant's reply text. Actual optimizer and allocator behavior needs measurement; do not assert quadratic copies as an established measured fact.
- Scaling: number of streamed fragments, size of accumulated argument and active decoder maps; final conversion/JSON parse is O(argument bytes). Large documents passed as tool arguments and many small deltas are the stress case. The decoder runs on the main actor.
- Smallest fix: maintain per-block fragment buffers in uniquely owned reference storage or an efficient chunk/byte accumulator and parse once on completion off the main actor where safe; preserve event ordering, error behavior and permission handling. Avoid exposing tool arguments in diagnostics.
- Confidence: high for control flow and main-actor placement, medium for copy-on-write cost in an optimized build.
- Mac measurement: feed identical 10 KB/1 MB argument payloads in 1, 100 and 10,000 deltas, instrument `accept` count/duration, cumulative bytes appended/copied and allocations, main-thread frame hitches and final decode; no content logging. Guard test: resulting decoded arguments and step sequence match for all fragmentations and counted bytes copied/concatenated are linear, not dependent on fragment count squared.

### DP-13 (P2, large fragmented helper-line suspect): Newline framing rescans the accumulated prefix
- `AtticAgentHelper/main.swift:206–213, 424–433`; `Attic/Agent/Run/AgentHelperClient.swift:285–315`.
- Both helper input/output framing and the app-side helper client append each chunk to an accumulating buffer, then search for the first newline from the beginning. A long JSON line arriving in many small chunks with no newline yet causes the already-searched prefix to be scanned again at each chunk. Complete lines are copied into `Data` and removed from the front. Each side has a 2,000,000-byte limit, so this is bounded, not an unlimited allocation. Work runs on the helper/client serial queues; delivery of parsed frames to the main actor follows. Distinct from DP-11's JSON-fragment value copying and PF-30's reply rendering.
- Scaling: with L bytes arriving in K small fragments, the no-newline search can examine O(L×K) bytes (quadratic in L for fixed-size fragments), plus line copies; actual Foundation buffer behavior and read chunk sizes require measurement. Large single-line tool payloads are the stress case.
- Smallest fix: maintain a newline scan offset across receives and process completed lines with a read cursor, compacting only periodically, while preserving byte limits, UTF-8/JSON validation, ordering and disconnect behavior.
- Confidence: high for repeated `firstIndex` from the buffer start, medium for real-world cost.
- Mac measurement: instrument bytes appended, bytes scanned, chunks, copied bytes, time on each serial queue and delay to `received` for 10 KB, 1 MB and near-limit line with 1/100/10,000 chunks; replay real helpers without logging message content. Guard test: fragmented input with embedded consecutive lines delivers identical ordered frames, malformed/oversize input fails closed, and scanned bytes stay O(total input).

### DP-14 (P2, dense-calendar suspect): Month marks and agenda repeatedly filter the whole fetched range on the main actor
- `Attic/Calendar/UI/CalendarPageModel.swift:320–350, 487–503` → `Attic/Calendar/UI/CalendarAgenda.swift:70–80, 105–108, 195–205`; sort comparator in `Attic/Calendar/CalendarEventSource.swift:67–69`.
- A Calendar rebuild maps tasks (cached by store revision/today/environment), gets the current range's events, then for every grid day calls `events(on:)`, which filters all events and sorts that day's matches even though the grid shows at most three dots. - Scaling: each actual body evaluation with nonempty query can scan T tasks + N notes and their candidate text lengths, then sort M matches O(M log M); fuzzy token comparisons and long stored bodies add work. Query edits, hover changes and other observed-model publications may trigger evaluations; exact SwiftUI counts require profiling. The returned list is capped at six only after the full scan/sort.
- Smallest fix: compute search only when the normalized query or relevant task/note search revision changes, cache normalized candidate tokens in a bounded, revision-invalidated index, and maintain a stable top-six selection while preserving score/tie ordering and complete matching semantics. Keep hover/highlight purely local; avoid stale results after edits/deletes.
- Confidence: high for body call and loops; main-actor duration and the frequency of evaluation require measurement.
- Mac measurement: signpost picker body and search; count calls, query normalizations, candidate/token/character visits and matches sorted while typing and moving hover at fixed query for 100/10,000 items and long stored bodies. Guard test: changing hover/focus with unchanged query and revision performs zero new candidate scans; an edited/deleted matching item invalidates correctly and top-six results match the current exhaustive algorithm, including ties and locale-sensitive normalization.

### DP-66 (P1 for large batches, suspect): Every imported file re-verifies the whole growing recovery payload
- Chain: `Attic/Notes/Session/NotesPageController.swift:3151–3207` loads files sequentially and checkpoints after every completed item, waiting for recovery work before loading the next. `liveByteInventory` (`:935–956`) includes every loaded staged payload; `journalEntry` and `journalStaged` independently build that inventory (`:2328–2351`). The durable journal `Attic/Notes/Session/NoteDraftJournal.swift:433–465` hashes each staged item and, when its staged file exists, reads it back for full byte equality on each write. It also uses `entry.staged.contains` inside a loop over staged items. I/O is performed on the journal’s I/O actor, not necessarily main; the next import item nevertheless waits for it, and inventory/document preparation is in the controller path.
- Scaling: with N equally sized newly staged files and no other changes, the sequence revisits approximately N(N+1)/2 payload instances across checkpoints, plus pre-existing staged material on each checkpoint; total bytes rehashed/read can grow quadratically with batch size. Metadata matching can likewise be O(N²) per checkpoint. Actual I/O cache and journal behavior affect elapsed time. This is distinct from DP-64’s waiting-task polling and from the existing PF findings.
- Smallest fix: retain the per-file durable recovery checkpoint, but store and verify immutable staged blobs once by ID/digest with safe ownership and atomic manifest updates, and index metadata by ID. Revalidate whenever bytes or ownership can have changed; do not skip integrity checks or expose a manifest before its bytes are durable. Preserve recovery of every completed and unfinished source after crash, conflict and concurrent writer.
- Confidence: high for serialized checkpoints and loops; their time contribution is unmeasured.
- Mac measurement: signpost each loader, checkpoint preparation, journal queue/wait and durable completion; count total hashes, bytes hashed/read/written, metadata comparisons and time-to-complete for 1/10/100 equal-size files, and crash at each file boundary. Guard test: N immutable inputs require O(N) blob verifications/byte writes rather than triangular repeated work while crash-recovery, corrupt-on-disk, conflicting-ID, ownership races and post-checkpoint mutation tests still refuse unsafe handoffs.

### DP-67 (P2, large-menu/AX suspect): Menu scroll and highlight updates rewrite every realized accessibility row
- Chain: `Attic/DesignSystem/Components/AtticGlassMenu.swift:401–423` routes pointer/scroll events; `AtticGlassMenuCard.scroll` (`:1109–1115`) and changed `setHighlight` (`:1134–1142`) call `AtticGlassMenuView.updateAccessibility` (`:2065–2071`). An accessibility client requesting `accessibilityChildren` (`:2046–2062`) realizes all item elements, including offscreen entries. The menu also creates one native entry view per entry when built (`:1849–1867`). This is separate from PF-44’s repeated submenu deadline on same-row hover: unchanged highlight is guarded, but scrolling and genuinely changed highlights still traverse all realized elements.
- Scaling: with E realized AX items, each changed scroll/highlight update performs O(E) frame/selection setter pairs; opening an E-entry menu creates O(E) native entry views and an AX children request can create O(E) accessibility objects. Cost depends on actual command counts and AX clients; not every menu is large, and no duration is measured.
- Smallest fix: on highlight-only changes update just old/new selection; on scroll expose accessibility frames computed lazily from current shared offset, or update only when an AX client asks, while retaining navigability and correct frames for offscreen items. Preserve all menu appearance, motion, keyboard/VoiceOver semantics and notifications; use native virtualization or lightweight drawing only if accessibility order and exact look are retained.
- Confidence: high for loops and guards, medium for user-visible impact with large menus.
- Mac measurement: count menu entries, created native views and AX elements, accessibilityChildren calls, per-event element updates, AX frame requests and time-to-first-frame with accessibility clients active and inactive for 10/100/1,000 commands. Guard test: highlight change updates at most the two affected selection elements; scroll need not write E frames, and all visible and offscreen AX rows report correct frame, selection and focus after scrolling.

### DP-68 (P2 at long-history scale): Conversion Undo/Redo compares version and association snapshots with nested linear searches
- Chain: `TaskNoteConversion.recordConversion` Undo/Redo (`Attic/TaskNote/TaskNoteConversion.swift:180–193`) → `ResultGuard.validateCurrent` (`:18–92`). For `.versions`, `.preservations` and `.noteAssociations`, it normalizes arrays then checks `old.allSatisfy { actual.contains($0) }`; the latter two also find extras using nested `contains` by owner. Preservation normalization may fetch/decode immutable preservation snapshots (lines 33–48). These checks protect later edits and replicas and must not be bypassed.
- Scaling: O(V_old × V_actual) semantic equality comparisons for versions, similarly O(A²/P²) in the respective association/preservation scope, plus normalization and any snapshot reads. Equality can inspect token replica fields; total depends on scope size, physical replicas and field sizes. It affects Undo/Redo of task/note conversion, not every typing Undo. The broad read-set fetch issue remains covered by PF-33; this is the subsequent comparison cost.
- Smallest fix: index normalized current tokens by stable owner/physical identity and, where useful, digest, then verify full semantic equality within the indexed candidates. Preserve duplicate multiplicity, exact version-subset rules, the permitted retired records and conflict refusal; never use a digest alone as proof where collision would matter.
- Confidence: high for nested loops; frequency and elapsed cost depend on long-lived history and require a Mac trace.
- Mac measurement: count scope members, semantic normalizations, preservation reads, equality comparisons and main-thread spans for 10/100/1,000 versions and multiple physical replicas during conversion Undo and Redo. Guard test: comparisons grow near-linearly for unique identities, while duplicate/changed/missing replicas and allowed or disallowed extra versions/associations produce identical decisions to the existing implementation.
